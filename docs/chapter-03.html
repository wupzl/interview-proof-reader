本章数字均为虚构教学示例。Little 定律适用于稳定系统的长期平均量，不能把任意峰值直接代入。

——一个工程师最危险的时刻，不是说不出系统有多快，而是说出了一个自己无法证明的数字。

第一幕：那句让人心脏骤停的话

2026 年，十月。

下午三点。

林远坐在电脑前，参加一家大型互联网公司的技术面试。

面试已经进行了四十分钟。

Java、MySQL、Redis、RAG、Agent，前面的问答都还算顺利。

面试官陈默翻到了简历的第二页。

他忽然停住。

“林远，你这里写着，你的企业级智能检索与问答平台，通过混合检索和重排序优化，检索效果提升了 35%。”

“对。”

“这个 35% 怎么来的？”

林远愣了一下。

“就是……通过混合检索，相比原来的向量检索，召回效果更好了。”

“我问的是，这个 35% 怎么算出来的？”

“就是优化前后做了对比。”

“比较的是什么指标？”

“召回率。”

“Recall@几？”

林远沉默了两秒。

“Recall@10。”

“测试集有多少条 Query？”

“……”

“每个 Query 的相关文档是谁标注的？”

“……”

“是人工标注，还是通过大模型生成的？”

“……”

陈默靠在椅子上。

“那你怎么确定提升了 35%，而不是 15% 或者 50%？”

林远的手心开始出汗。

陈默没有继续逼问。

他只是说：

“我们先跳过这个问题。”

但接下来，他在面试评价里写下了一句话：

候选人对项目原理比较熟悉，但部分性能指标缺乏可验证的实验依据。

林远不知道的是，这句话的影响，可能比他少答对三道八股题还要大。

因为它不仅涉及技术深度。

还涉及一个更加敏感的问题。

你的技术陈述，究竟有多可信？

第二幕：数字为什么会反过来伤害你？

晚上。

林远来到周衡的办公室。

“老师，我感觉这次面试不应该挂。”

“为什么？”

“我项目原理都回答出来了，手撕也做出来了。就是数据被问住了。”

周衡抬起头。

“你知道数据被问住，意味着什么吗？”

“说明我不太懂性能评测？”

“有这个可能。但还有另一种解释。”

“什么？”

周衡看着他。

“面试官可能开始怀疑，你简历里其他没有被验证的说法，是不是也不够准确。”

林远沉默了。

周衡拿过一张纸。

在上面写下：

技术能力 ≠ 技术陈述的可信度

“假设两个候选人。”

“候选人 A 告诉我，他把系统性能提升了 300%，但是不知道测试环境、负载模型，也不知道指标怎么算的。”

“候选人 B 告诉我，他做过一次本地压测，优化后 P95 延迟从 420ms 降到 310ms，能够给我看完整的压测脚本、原始数据和环境配置。”

“你更相信谁？”

“B。”

“为什么？”

“因为 B 的数据能验证。”

“对。”

周衡敲了敲桌子。

“面试官不一定要求应届生做出多么惊人的性能提升。”

“但是，如果你主动给出了定量指标，你就要承担解释它的责任。”

“数字越精确，越容易让人期待相应精度的证据。”

第三幕：四种数字，四种不同的陷阱

周衡打开一份模拟简历。

里面有四条经历。

系统支持 10,000 并发

陷阱：并发连接数、在途请求数与 QPS 并不是一回事。

接口响应时间降低 60%

陷阱：究竟比较平均延迟、P95、P99，还是某个单次请求？

RAG 召回率达到 95%

陷阱：测试集、相关性标注、K 值、计算口径是否明确？

Token 成本降低 40%

陷阱：比较的任务是否相同？质量是否下降？是否包含重试和工具调用成本？

“这四种数字有什么共同点？”

林远想了想。

“都需要说明统计方式。”

“还不够。”

周衡说：

“它们都需要回答五个问题。”

他在白板上写下：

  1. 对象： 测量的究竟是什么？
  2. 基线： 与谁比较？
  3. 环境： 在什么条件下测量？
  4. 方法： 如何采集和计算？
  5. 结果： 是否可以重复得到相近的结论？

“只要你主动写了数字，最好就能对这五个问题给出答案。”

“我们一个个来看。”

第四幕：一万并发的谎言

“假设你简历里写着：系统支持一万并发。”

周衡说。

“我先不怀疑你。”

“我只问你，一万并发是什么意思？”

林远回答：

“一万个请求同时处理。”

“如果一万个客户端建立 SSE 长连接，但每个连接只有很少的数据传输，这算一万并发吗？”

“算一万个并发连接。”

“那一万 QPS 呢？”

“是一秒处理一万个请求。”

“如果一万个请求的平均响应时间是 100ms，需要多少平均在途请求？”

林远开始计算。

周衡在白板上写下：

L = λ × W

L = 10,000 × 0.1 = 1,000

“在稳定系统中，按照 Little 定律，平均在途请求数约为 1000。”

“所以，一万 QPS 不等于一万个并发请求。”

林远点头。

“那如果是一万个 SSE 连接？”

“这意味着同时维持一万个连接，但并不能直接说明系统能处理一万 QPS，也不能证明它能够稳定完成一万个同时进行的模型推理。”

周衡继续：

“你做的是 AI 应用，尤其需要注意这件事。”

“一个普通 CRUD 接口可能几十毫秒完成。”

“但大模型流式生成请求可能持续几十秒。”

“假设每秒有 100 个新请求，每个请求平均持续 30 秒。”

L = 100 × 30 = 3,000

“在稳定情况下，平均在途请求数可能达到 3000。”

“这还只是平均值，不代表峰值。”

“所以，如果你在简历上写‘支持一万并发’，面试官当然要问清楚。”

你可以怎样准确描述？

实际验证内容 更准确的表述
维持 10,000 个 SSE 连接 测试环境下维持 10,000 个并发 SSE 连接
达到 10,000 QPS 指定负载下吞吐量达到 10,000 req/s
1000 个用户同时发送请求 模拟 1000 个并发请求，记录吞吐量与延迟
没有实际压测 完成并发架构设计，尚未验证承载上限

“面试官真正希望看到的，不是你把数字写得尽可能大。”

“而是你知道每个数字代表什么。”

第五幕：第一次真正的性能实验

第二天。

周衡带林远来到公司的测试环境。

“今天不背八股。”

“我们设计一场真正可解释的压测。”

林远打开自己的 Spring Boot 项目。

周衡说：

“先选择一个足够明确的测试对象。”

“比如你的检索接口。”

“我们先假设它接收一段 Query，然后返回检索结果。”

“如果你的接口还要调用外部大模型，那要么单独测完整链路，要么明确使用模拟模型服务。不能把两者的数据混在一起。”

林远点头。

周衡继续：

“今天所有的性能数值都只是教学示例，不代表你项目的实际成绩。”

实验一：建立基线

两人开始设计压测。

测试配置（虚构实验示例）

项目 配置
服务 Spring Boot 检索接口
CPU 4 vCPU
内存 8 GiB
测试数据 固定的 10 万条文档
压测工具 k6
请求负载 固定测试 Query 集
负载模式 稳定速率，逐级增加
观察指标 QPS、P50/P95/P99、失败率
预热 单独预热，不计入正式结果

“为什么要固定测试数据？”

“避免前后两次请求的数据规模不同。”

“为什么要预热？”

“减少 JIT 编译、连接建立、缓存冷启动等因素对正式测量的影响。”

“很好。但要注意，如果你就是想测冷启动或者缓存未命中，那就需要另设实验，不应该把这些影响全部消除。”

“为什么还要记录 CPU 和内存？”

“因为性能变化可能来自资源瓶颈，而不仅仅是代码。”

周衡点头。

“现在我们假设测出下面这组数据。”

示例：优化前后延迟对比

优化前

优化后

0 ms250 ms500 ms750 ms1000 msP50P95P99

纯教学示例，非用户项目实测数据

同一测试条件下的一组假设结果。实际测试应多次重复，并报告波动区间及吞吐量、错误率。

“现在计算一下 P95 的改善幅度。”

林远写下：

(420 − 310) ÷ 420 × 100% ≈ 26.2%

“所以，我们应该写性能提升 26.2%？”

周衡摇头。

“更准确地说，是在这组假设测试条件下，P95 延迟下降约 26.2%。”

“为什么？”

“因为性能有很多维度。”

“平均延迟、尾延迟、吞吐量和资源消耗，可能变化方向不一致。”

“P95 降低 26.2%，不代表整个系统的所有性能指标都提升 26.2%。”

林远点点头。

这一次，他真正理解了数字应该如何描述。

第六幕：面试官最喜欢问的一句话——‘为什么会变快？’

下午。

陈默再次出现。

他看着那组教学示例数据。

“好，假设你的 P95 从 420ms 降到了 310ms。”

“为什么变快？”

林远回答：

“因为增加了 Redis 缓存。”

“具体缓存了什么？”

“检索结果。”

“缓存命中率是多少？”

“……”

“如果缓存命中率只有 5%，你觉得它能解释这个改善吗？”

“未必。”

“如果你的两次压测分别使用了不同 Query 呢？”

“那结果可能不可比。”

“如果第二次压测前，操作系统 Page Cache 已经被预热了呢？”

“也可能导致延迟降低。”

“如果只是因为第二次压测时外部依赖负载比较低呢？”

“也会影响结果。”

陈默点头。

“所以，我要的不是你告诉我‘加了缓存所以变快’。”

“我要的是你建立因果证据。”

他在白板上画了一张表。

观察结果 可以支持的结论 还不能证明什么
P95 下降 测量的尾延迟有所改善 一定由 Redis 导致
缓存命中率提高 更多请求命中了缓存 整体延迟必然下降
数据库查询次数减少 缓存减少了部分数据库访问 系统所有瓶颈已经解决
多次重复测试趋势一致 结果更稳定 在所有生产场景都有效

“那应该怎么验证？”

林远思考。

“可以做控制变量实验。”

“展开。”

“保持代码版本、机器配置、数据规模和请求负载一致，比较开启缓存和关闭缓存两种配置。”

“同时记录命中率、数据库查询次数和查询耗时。”

“如果开启缓存后，数据库访问次数确实降低，并且端到端延迟在多次重复实验中稳定改善，那就能更有把握地认为缓存是改善的重要原因。”

陈默继续：

“还有呢？”

“需要确认错误率没有上升，而且缓存一致性符合业务要求。”

陈默点头。

“这才是性能优化的回答。”

第七幕：一场关于 RAG 召回率的审判

傍晚。

周衡突然拿出了林远之前最害怕的那个问题。

“你的 RAG 召回率达到 95%，怎么证明？”

林远深吸一口气。

“首先需要明确指标。”

“很好。继续。”

“比如 Recall@10，通常需要有带相关性标注的 Query 集合。”

“对于每个 Query，设相关文档集合为 G_q，前 10 条检索结果为 R_q¹⁰，那么：”

Recall@10(q) = |G_q ∩ R_q¹⁰| ÷ |G_q|

“对于每个有相关文档标注的 Query 计算，然后求宏平均。”

周衡点头。

“假设有 100 个查询，每个查询只有一个标准答案 Chunk，结果其中 95 个查询在前十条找到了正确 Chunk，你能叫它 Recall@10 达到 95% 吗？”

林远想了想。

“在每个查询只有一个标注相关 Chunk 的前提下，宏平均 Recall@10 确实等于 95%，同时 Hit Rate@10 也是 95%。”

“但如果一个查询可能有多个相关 Chunk，那么 Hit Rate@10 和 Recall@10 就不相同了。”

“非常好。”

“那如果你的测试集只有十个问题？”

“结论的稳定性和代表性不足。”

“如果测试集是大模型自己生成的呢？”

“也不是完全不能用，但可能存在生成偏差、答案泄漏或对特定检索方式有利的问题，需要人工抽样审查，并尽量使用独立的测试集。”

周衡笑了。

“现在我再问。”

“如果你的 Recall@10 提高了，但最终回答质量下降了呢？”

林远停顿了一下。

“那说明召回指标不能代表完整 RAG 效果。”

“原因可能是新增召回结果包含更多无关信息，增加了上下文噪声；也可能是 Reranker、Prompt 组织或生成阶段存在问题。”

“所以除了检索指标，还要评估最终答案的准确性、Faithfulness、引用正确性和延迟成本。”

周衡放下笔。

“你终于不再把 RAG 评测当成一个百分比了。”

第八幕：指标真的越高越好吗？

周衡突然问：

“假设两个 RAG 系统。”

“A 系统 Recall@10 达到 95%，平均响应时间 15 秒。”

“B 系统 Recall@10 达到 92%，平均响应时间 2 秒。”

“你选哪个？”

林远回答：

“要看业务。”

“为什么？”

“如果是需要严格检索证据的专业场景，召回率差异可能更重要；如果是普通企业知识问答，用户对响应速度也非常敏感。”

“而且还需要看 95% 和 92% 的差异是否稳定，以及最终答案质量有没有差异。”

“对。”

周衡说：

“做技术方案，不是为了让某一个数字达到最大。”

“而是优化业务目标下的整体效果。”

他写下：

方案价值 = f(质量，延迟，成本，可靠性)

“这是概念表达，并不是让你真的把所有指标直接相加。”

“不同业务，对这些因素的权重完全不同。”

“你知道为什么大厂面试官喜欢问这种问题吗？”

“因为真实工程里没有无限资源？”

“对。”

“所有方案都存在代价。”

“你增加 Reranker，可能改善排序质量，但增加延迟。”

“你增加召回数量，可能改善覆盖率，但也可能引入噪声。”

“你增加缓存，可能降低成本，但需要解决失效和一致性。”

“你增加 Agent 的工具调用次数，可能提高问题解决成功率，但也会增加 Token 成本、执行时间和出错机会。”

“成熟的工程师，不是永远选择最复杂的技术。”

“而是知道什么时候复杂性值得付出。”

第九幕：Coding Agent 的另一场危机

第二天。

林远准备了一份 Coding Agent 项目介绍。

周衡看着简历上的描述：

“基于大模型的自动代码修复 Agent，可自动定位代码缺陷、验证 Bug 并生成补丁，大幅提升修复效率。”

周衡皱眉。

“这句话有什么问题？”

林远想了想。

“大幅提升修复效率，没有具体指标。”

“还有呢？”

“自动定位、验证和修复也需要明确能力边界。”

“对。”

周衡问：

“如果我要你证明这个 Agent 真的能够修复 Bug，你会怎么设计评测？”

林远思考片刻。

“首先建立一组具有可复现失败测试的 Bug 样本。”

“然后让 Agent 在固定的模型、工具权限、执行环境和预算下，完成定位、补丁生成与验证。”

“对于每个任务，判断最终补丁是否成功通过规定的测试。”

周衡继续：

“只要测试通过，就算成功吗？”

林远摇头。

“不一定。”

“如果测试覆盖不足，Agent 可能只是绕过了失败条件。”

“或者为了让测试通过，直接删除了断言，甚至修改了测试代码。”

“很好。”

“所以你会如何定义成功？”

林远在白板上写下：

Coding Agent 修复效果评测框架

维度 关注内容
Bug 复现率 能否在隔离环境复现目标问题
Patch Validity 补丁能否正确应用、构建
Test Pass Rate 是否通过指定测试
Regression 是否引入已检测到的回归问题
Resolution Rate 经验证真正解决问题的任务比例
Cost Token、工具调用、计算资源成本
Latency 完成任务所需的时间
Safety 是否越权修改文件、执行危险操作

周衡点头。

“还要明确哪些指标是自动测试结果，哪些需要人工审查。测试通过率不等于真实问题解决率。”

“比如你用了 SWE-bench 类似的评测思想，也需要说清楚你是否真的在对应基准上运行过，不能拿自建小样本测试结果冒充公开基准成绩。”

林远点头。

“那简历应该怎么写？”

“如果你没有实测数字，就不要强行写数字。”

周衡给了他两个版本。

缺少证据的描述

“自主研发高性能 Coding Agent，实现全自动 Bug 修复，修复准确率高达 98%，效率提升 80%。”

有明确工作边界的描述

“参与构建基于大模型的代码缺陷分析与修复链路，围绕仓库代码检索、问题复现、补丁生成及测试验证设计 Agent 工作流，并对失败重试、验证结果和执行安全性进行分析。”

“第二版虽然没有惊人的数字，但前提是真实经历，也完全可以成为不错的项目描述。”

“如果以后有了真实评测，再补充指标。”

“而且最好附带样本量、任务类型和测试环境。”

第十幕：那些漂亮数字，可能掩盖了什么？

晚上。

周衡给林远看了一份虚构的压测报告。

上面写着：

“系统最高吞吐量：5000 QPS。”

林远看了一眼。

“挺高的。”

“你再看下面。”

报告里还有几项信息。

同一次压测的其他指标

指标 示例值
吞吐量 5,000 req/s
P99 延迟 8.6 秒
失败率 17%
CPU 利用率 99%

虚构的教学示例，QPS 的成功请求与失败请求计数口径仍需要单独说明。

“你觉得这个系统怎么样？”

林远犹豫了。

“吞吐量虽然高，但失败率达到 17%，P99 也非常差。不能认为系统能够稳定承载 5000 QPS。”

“对。”

“那如果有人只把 5000 QPS 写进简历呢？”

“就会产生误导。”

周衡点头。

“这就是为什么性能指标不能脱离约束条件。”

“在真实业务中，通常需要定义一个服务质量目标。”

“比如 P95 小于 500ms，失败率低于 0.1%。”

“然后寻找在这些约束下能够稳定维持的最大吞吐量。”

“而不是单纯找压测工具显示的最高 QPS。”

林远突然想到了什么。

“所以系统的最大承载能力，其实必须结合服务质量要求定义？”

“对。”

“如果延迟无限上涨、请求大量失败，即使表面上有很高的吞吐量，也不代表业务可接受。”

第十一幕：如何在面试官质疑时回答？

第三天。

周衡决定模拟最困难的情境。

他扮演一位比较强势的面试官。

“你简历里说 RAG 效果提升了 35%，我感觉这个数字不太可信。”

林远一开始有些紧张。

但他很快调整了表达。

“您这个质疑是合理的，因为这个数字需要明确评测口径。”

“如果我已经有完整测试数据，我会先说明使用的 Query 集合、标注方式、对照方案和具体指标，再解释结果。”

“如果只是早期实验得到的结果，我会明确它的局限，比如测试集规模偏小、缺少重复评测，或者结果只能说明特定数据集上的表现。”

周衡继续：

“那你到底有没有完整数据？”

林远回答：

“如果没有，我就不能把它当成经过充分验证的工程结论。”

“我会承认当时对指标定义和评测严谨性考虑不足，同时把可以证明的工作内容讲清楚，例如具体实现过的检索链路和已做过的实验。”

周衡放下笔。

“非常好。”

“注意，你不是靠话术把不存在的证据变出来。”

“而是避免进一步损害可信度。”

他停了一下。

“但是，如果面试官问你‘这个数字怎么来的’，你已经知道它只是估计，就应该直接说明，而不是先编一套方法。”

“面试官不一定因为一个指标不严谨就否定全部技术能力。”

“但如果发现你连续给出不真实的解释，那就完全不同了。”

第十二幕：数字背后的工程师

一周后。

林远再次参加了一场技术面试。

面试官翻到了他的 RAG 项目。

“你写到通过检索链路优化改善了系统响应速度，可以介绍一下吗？”

这一次，林远没有上来就报一个百分比。

“可以。我会先区分检索阶段的耗时和整个问答接口的端到端延迟。”

“因为 RAG 系统的响应时间还受到大模型生成、网络和重排序的影响，所以不能把检索优化直接等同于整个系统的同比例提升。”

“我主要关注的是检索链路里哪些步骤产生了额外开销，以及这些步骤带来的效果收益是否值得。”

面试官点头。

“你怎么判断？”

“我会先设置基线，比如纯向量检索方案，然后在相同数据集、相同 Query 和相同资源条件下，比较混合检索与重排序方案。”

“除了 Recall@K 和 nDCG，还需要观察检索 P95 延迟，以及最终答案质量。”

“这样才能判断是单纯增加了检索复杂度，还是确实形成了有效改善。”

面试官继续：

“那你实际完成了哪些实验？”

林远没有回避。

他打开了自己的实验记录。

对于真正做过的部分，他给出具体的测试方法、参数和结果。

对于还没有验证的部分，他明确说明仍处于设计阶段。

面试官问：

“如果你有机会继续做这个项目，最优先补充什么？”

林远回答：

“我会优先建立可复用的评测集和观测体系。”

“因为没有稳定的基线，就很难判断每次检索策略调整究竟改善了什么。”

“而如果没有链路追踪和分阶段耗时统计，即使用户反馈系统变慢，也很难快速定位问题。”

面试官点头。

“你的答案不是最复杂的。”

“但是能看出你知道该怎么验证一个工程方案。”

林远忽然意识到：

过去，他总觉得项目必须有足够漂亮的数字，才能证明自己的能力。

现在，他开始理解：

真正能体现工程能力的，不只是结果有多好，还有你是否知道如何测量结果、解释结果，以及识别结果的局限。

终章：周衡的五条铁律

最后一天。

周衡在白板上写下五句话。

  1. 没有实验依据，不写精确指标。

可以描述已经完成的功能和技术设计，但不要把预期收益写成实际成绩。 2. 有指标，就准备完整的证据链。

至少清楚说明测试对象、基线、环境、计算方法及结果。 3. 性能优化必须有因果解释。

观察到改善不代表已经证明改善来自某个优化措施。 4. 不要只选择对自己有利的数字。

吞吐量、延迟、错误率、资源成本和质量指标应该结合分析。 5. 面对质疑，准确比强硬更重要。

已经验证的就给证据；还没有验证的就说明边界，绝不临时编造数据。

周衡问：

“林远，你现在还觉得面试官质疑你的性能指标，是在否定你这个人吗？”

林远摇头。

“不觉得了。”

“他真正需要判断的是，我的结论是否有足够的依据。”

“如果我确实做过实验，就应该能说清楚。”

“如果我没做过，就应该承认没有做过。”

“至于我的技术能力，应该通过实现、推理、测试和问题解决能力来展示，而不是依靠一个夸张的百分比。”

周衡笑了。

“很好。”

“这才是一个工程师应该有的态度。”

林远收拾好电脑。

临走前，他又问了一句：

“老师，如果我技术理解不错、项目也确实是自己做的，但我就是不擅长把复杂的事情讲得简洁，该怎么办？”

周衡沉默了一会儿。

然后说：

“那我们下一次，就不再学习如何证明项目。”

“而是学习更困难的一件事。”

“什么？”

“如何控制面试官的注意力。”
