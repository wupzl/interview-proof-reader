# 第6章 · 被记住的人

——技术面试最残酷的事情，不是面试官不相信你，而是面试结束后，他根本说不清你和其他候选人有什么区别。

## 第一幕：五份几乎一模一样的简历

2026 年，深秋。

北京，某大型互联网公司研发中心。

下午六点。

技术负责人陈默坐在会议室里，面前摆着五份校招生的简历。

这一天，他已经面试了五个人。

五个人都学过 Java。

五个人都了解 MySQL、Redis。

其中四个人做过 RAG 项目。

三个人做过 AI Agent。

甚至连简历中的项目名称都惊人地相似。

《基于大模型的企业智能知识问答平台》

《企业级 RAG 智能检索系统》

《基于 LangChain 的 AI Agent 平台》

《多模型智能对话与知识管理系统》

陈默揉了揉太阳穴。

“怎么感觉今年所有人做的都是同一个项目？”

坐在旁边的面试官李工笑了。

“而且技术栈基本都一样。”

“Spring Boot、Redis、MySQL、向量数据库、Embedding、Reranker。”

“介绍项目的时候，都是文档解析、向量化、检索、生成。”

陈默点点头。

“但今天有两个人，我印象比较深。”

“哪两个？”

“一个叫许航。”

“他做的也是 RAG，但他对检索评测很熟悉。”

“另一个叫林远。”

“他讲 Agent 的时候，没有一直强调模型多聪明，反而一直在讨论怎么验证模型生成的补丁。”

李工翻开面试记录。

“那另外三个人呢？”

陈默沉默了几秒。

“技术基础可能都还可以。”

“但是……”

他又翻了一遍简历。

“我一时想不起来他们各自最擅长什么。”

与此同时。

几十公里外。

林远正在和周衡复盘自己的面试。

他还不知道，这一天，他已经第一次成为了一个能被面试官清楚描述的候选人。

## 第二幕：为什么“我什么都会”有时反而没有优势？

周衡打开林远的简历。

“你先介绍一下自己的技术能力。”

林远开始说：

“我主要学习 Java 后端开发，熟悉 Spring Boot、Spring Security、MyBatis、MySQL、Redis，也了解 JVM、并发编程、计算机网络和操作系统。”

“然后还有 AI 相关的 RAG、Agent、Embedding、向量数据库、LangChain、Function Calling、多模型适配，以及 Vue 前端……”

他说了整整一分钟。

周衡突然打断。

“停。”

“假设我刚刚面试了十个人。”

“其中八个人都说了你刚才这些东西。”

“你觉得我能记住你吗？”

林远沉默了。

“应该很难。”

“对。”

周衡说：

“技术栈广泛是优点，但技术名词本身不构成差异。”

“尤其是应届生招聘。”

“大家都学 Java。”

“大家都写过 CRUD。”

“现在又有很多人做过 RAG 和 Agent。”

“如果你的自我介绍只是工具和框架的排列组合，那么面试官很难建立对你的清晰判断。”

林远皱眉。

“所以我要强调自己最擅长的领域？”

“是的。但我要纠正一个误区。”

“个人技术定位，不是给自己起一个厉害的称号，而是让别人能够用一句准确的话概括你的真实优势。”

周衡在白板上写下三个例子。

定位 A：泛化标签

“熟悉 Java、Redis、MySQL、RAG、Agent、微服务和前后端开发。”

信息丰富，但不能直接判断最突出的能力。

定位 B：技术方向

“主要关注 Java 后端与 AI 应用工程，对 RAG 检索链路和模型服务集成有较深入的学习与实践。”

能看出方向，但还需要具体证据。

定位 C：证据驱动

“以 Java 后端为基础，重点研究 AI 应用从模型调用到可靠执行的工程问题，能够结合具体项目解释检索、工具调用、异常处理和验证机制的设计取舍。”

能否采用这一定位，取决于是否具有足够真实的实现与分析证据。

周衡问：

“你觉得哪个更容易记住？”

“C。”

“为什么？”

“因为我大概知道这个人更关注什么问题。”

“对。”

“但请记住。”

“一个定位只有在后续问答中被证实，才真正有价值。”

“否则只不过是另一句漂亮的自我评价。”

## 第三幕：面试官真正记住的，不一定是你做过多少功能

第二天。

周衡安排了一场特殊实验。

他让林远分别扮演三个候选人。

三个人都做过 Coding Agent。

但项目介绍不同。

### 候选人 A：功能丰富型

林远说：

“我开发了一个 Coding Agent，支持代码仓库分析、自动 Bug 定位、自动修复、测试验证、多工具调用、任务管理、流式输出和前端可视化。”

周衡问：

“听上去功能不少。”

“但你最想让我记住什么？”

林远回答：

“项目功能很完整。”

“这当然是一种优势。”

“但是没有代码、演示和验证记录时，面试官无法只凭介绍判断每项功能的完成质量。”

### 候选人 B：技术名词型

林远换了一个说法：

“项目基于 ReAct Agent 架构，结合 Function Calling、MCP、代码检索、上下文压缩、Docker 沙箱和多 Agent 协作，实现自动化软件开发。”

周衡继续：

“技术名词很多。”

“但这些名词之间的关系是什么？”

“为什么需要多 Agent？”

“什么时候单 Agent 不够？”

“沙箱到底隔离了哪些资源？”

“工具调用失败怎么恢复？”

林远没有立即回答。

周衡点头。

“你发现了吗？”

“只要说出一个高级技术名词，面试官就有理由验证它。”

### 候选人 C：工程问题型

林远第三次开口。

“这个项目主要尝试解决代码缺陷定位与修复的自动化问题。”

“我认为它最困难的部分，不只是让模型生成看起来合理的补丁，而是判断补丁是否真的解决了问题。”

“因此，我重点关注 Bug 复现、工具执行、测试验证以及修复后回归检查之间的关系。”

“例如，模型可能生成一个能够通过已有测试的补丁，但由于测试覆盖不足，实际问题仍然存在。”

“所以需要区分测试通过、目标 Bug 解决，以及是否产生回归问题。”

周衡突然问：

“你这个观点从哪里来的？”

林远回答：

“我可以从参与项目时接触到的验证链路讲起，同时区分我实际实现的模块和目前还只是研究的方案。”

周衡点头。

“很好。”

“这次你的回答有一个明确的核心。”

“Agent 可靠性。”

“面试官至少知道，你在这个项目里最值得被追问的方向是什么。”

林远问：

“那我是不是应该每次都强调 Agent 可靠性？”

“不是。”

周衡摇头。

“如果你对这个问题只是理论理解，没有多少真实实践，那它可以作为技术兴趣，但不应该包装成已经具备的核心工程成果。”

“更不能因为我说这个方向容易形成记忆点，你就把自己的所有经历往这个方向硬套。”

“真正有效的技术定位，是从证据里总结出来的，而不是先想一个标签，再编故事证明它。”

## 第四幕：面试官脑海中的候选人画像

晚上。

周衡给林远展示了一份虚构的面试评价记录。

“你看这三份反馈。”

候选人 A

印象模糊

“Java 基础尚可，有 AI 项目经验，了解 RAG 和 Agent，部分工程细节回答一般。”

候选人 B

方向明确

“主要做 Java 后端，数据库与并发基础扎实，对缓存和线程池的技术取舍理解较好。”

候选人 C

证据清晰

“有 AI 应用工程实践，能较深入解释 Agent 执行验证链路，能够结合真实实现讨论故障边界和测试设计；基础后端能力符合要求。”

以上均为虚构的评价示例，不代表任何公司的真实招聘评语或评分标准。

周衡说：

“你现在知道什么叫被记住了吗？”

林远回答：

“面试官能够清楚说出我的技术优势，并且知道具体证据。”

“对。”

“但是你还要注意一件事。”

“什么？”

“被记住不等于被录用。”

“如果岗位要求很强的计算机网络基础，而你网络基础不足，即使你 Agent 理解很好，也未必通过。”

“如果岗位主要做高性能 C++，你的 Java AI 项目再有特色，也未必匹配。”

“因此，技术定位不能代替岗位匹配。”

“它只是帮助面试官更有效地理解，你在哪些方面有相对优势。”

## 第五幕：一个真正困难的问题——你的优势究竟是什么？

周衡关上电脑。

“现在我们讨论你。”

“你觉得自己的最大优势是什么？”

林远思考了一会儿。

“我会 Java 后端。”

“这不够具体。”

“我做过 AI 项目。”

“很多人都做过。”

“我对 RAG 和 Agent 理解得比较深入。”

“深入到什么程度？”

林远沉默了。

周衡继续：

“你能不能现场设计一个检索实验？”

“能。”

“能不能解释 BM25、向量检索、RRF 的主要区别？”

“能。”

“能不能把一个 Agent 的任务状态机设计出来？”

“应该可以。”

“能不能讲清楚自己亲自处理过的三个真实 Bug？”

“可以找项目记录。”

“能不能给出一组严格可复现的线上压测数据？”

林远停顿了一下。

“目前不一定能。”

“很好。”

周衡说：

“现在我们开始看到一个相对真实的能力轮廓。”

“你不是所有领域都达到同样深度。”

“你可能在 AI 应用机制、系统设计和 Java 实现方面积累较多。”

“而真实生产环境验证、线上故障经验，可能还需要继续补充。”

“这不是评价你的价值。”

“而是明确你的能力结构。”

他在白板上画了一张图。

技术能力画像：示意图

纯示意图，不是对你实际能力的打分。真实能力画像应结合代码、项目记录、现场测试和面试表现确定。

“你要做的，不是把这张图每一个方向都吹成满分。”

“而是找到一个岗位真正需要、同时你有证据证明的优势。”

“然后，在面试中稳定地展示它。”

## 第六幕：技术深度，不是把源码从头背到尾

第二天。

陈默再次来到会议室。

“我今天只考一个问题。”

“你说自己对 Agent 理解比较深入。”

“那你告诉我，Agent 和普通的 LLM API 调用有什么区别？”

林远回答：

“普通的模型调用主要是输入上下文、输出结果。”

“Agent 系统则通常围绕任务目标构建循环执行过程，通过模型进行决策，再调用工具观察结果，并根据反馈决定下一步动作。”

陈默点头。

“那如果模型一直调用同一个工具，陷入死循环怎么办？”

林远回答：

“需要设计执行边界，比如最大迭代次数、时间预算、Token 预算，以及检测重复工具调用和重复状态的机制。”

“最大迭代次数设置多少合适？”

林远思考。

“这个不能脱离任务类型直接给出一个通用数字。”

“简单信息检索任务和复杂代码修复任务，合理的执行步骤差异很大。”

“可以先根据任务复杂度设置基础预算，再通过历史执行轨迹分析失败率、完成率和成本分布，调整限制。”

陈默继续：

“那如果 Agent 已经执行了 20 步，第 21 步失败，你是让它全部重来，还是从第 20 步恢复？”

林远没有立即回答。

他先确认：

“这里要区分失败类型。”

“如果是短暂的工具调用失败，可以考虑从最近的可靠状态重试。”

“如果前面的操作已经产生副作用，比如写入数据库、修改代码或提交外部请求，就不能直接把所有工具调用重新执行一遍。”

“因为重试可能导致重复操作。”

“所以需要任务状态持久化、操作幂等性设计，以及对不可逆副作用的特殊处理。”

陈默问：

“如果是代码修复 Agent，你怎么保证补丁应用是幂等的？”

林远回答：

“我不会假设补丁应用天然幂等。”

“需要结合具体工具的行为，例如检测补丁是否已应用、校验工作区版本和目标文件状态，必要时使用版本控制建立恢复点。”

“在失败恢复时，应先确认当前工作区状态，再决定继续、重新生成补丁还是回滚。”

陈默继续：

“如果 Agent 修改了五个文件，第三个文件修改失败了呢？”

林远回答：

“如果要求整个补丁具有一致性，直接逐个原地修改可能留下部分成功状态。”

“可以考虑先在临时工作区生成修改、执行检查，再以受控方式提交结果；或者依托 Git 工作树、提交记录等机制进行回滚和恢复。”

“但具体实现还需要考虑并发任务是否共享工作区，以及用户是否允许自动覆盖已有修改。”

陈默终于笑了。

“这次不错。”

他在记录里写下：

候选人能够围绕 Agent 执行状态、工具副作用和失败恢复进行连续推理，理解相关工程约束。

林远没有看到这句话。

但他感受到了变化。

他不再把技术深度理解成知道多少术语。

而是能够围绕同一个问题，不断分析新的约束。

## 第七幕：真正的差异化，是别人追问三次以后才出现的

面试结束后。

周衡问林远：

“刚才第一道题，Agent 和普通 LLM API 有什么区别，难吗？”

“不难。”

“很多候选人都会。”

“第二道题，死循环怎么处理？”

“也不算很难。”

“第三道题，失败恢复怎么处理？”

“开始需要思考。”

“第四道题，部分文件修改成功怎么办？”

“就比较考验工程设计能力了。”

周衡点头。

“你发现了吗？”

“真正的差异化，往往不是第一层答案。”

“第一层答案可能所有人都会。”

“第二层也可能差不多。”

“但到了第三层、第四层，候选人的知识结构和实际经验就开始分化。”

“有人只会说加 Redis。”

“有人能解释锁、重试、幂等和状态一致性。”

“有人不仅能够解释，还能讲出自己遇到过的故障、代码修改和验证过程。”

“这些层次并不完全等价。”

“所以，你要找到自己真正能够被连续追问的几个技术主题。”

林远问：

“要准备多少个？”

“对于一场以项目为核心的技术面试，我建议先精心准备三到五个。”

“不是因为这个数字有什么魔法。”

“而是因为人的准备时间有限，只有几个主题真正深入，才容易形成稳定的技术证据。”

## 第八幕：给自己准备三张王牌

周衡拿出林远的三个项目方向。

“我们不要追求所有项目都讲成顶级架构。”

“先给每个项目确定一个你确实掌握的核心问题。”

王牌一：RAG 检索可靠性

从语义召回到可验证的知识检索

核心追问方向： Chunk 设计、BM25、向量召回、RRF、Reranker、Recall@K、评测数据集与延迟权衡。

王牌二：Coding Agent 执行与验证

从模型生成补丁到验证真实修复

核心追问方向： 代码上下文、工具调用、执行状态、隔离环境、Bug 复现、回归测试、失败恢复与安全边界。

王牌三：Java AI 服务工程

从模型 API 接入到稳定的服务链路

核心追问方向： Spring WebFlux、SSE、阻塞调用、背压、超时取消、数据库持久化、并发控制与性能观测。

这些是结合你的项目方向设计的候选技术主题。正式面试应选择你有真实代码、调试经验和验证证据的部分，而不是把所有主题宣称为已完成的工程成果。

周衡说：

“这三张王牌有一个共同点。”

“什么？”

“它们不是孤立的技术栈。”

“而是三个完整的问题领域。”

“RAG 的问题是怎么检索到可靠证据。”

“Agent 的问题是怎么让模型生成的操作可靠执行。”

“Java AI 服务的问题是怎么把模型能力稳定地交付给用户。”

“这三个主题可以共同构成一个技术方向。”

林远慢慢地说：

“AI 应用工程化？”

“可以。”

周衡点头。

“不过不要因为给它起了名字，就认为你已经具备所有相关能力。”

“定位是你持续积累能力的方向，也是面试中帮助别人理解你的线索。”

“不是能力认证。”

## 第九幕：为什么有时候展示缺点，反而更可信？

夜晚。

周衡继续问：

“如果面试官问，你的 Agent 项目还有哪些不足，你会怎么回答？”

林远说：

“比如目前对于长任务的失败恢复、工具调用追踪和验证覆盖率，可能还需要进一步完善。”

“如果这是事实，可以。”

“但如果我继续问，你为什么认为这些问题重要呢？”

林远想了想。

“因为 Agent 和传统接口不同，它可能连续执行多次模型决策和工具调用。”

“中间任何一次操作失败，都可能影响后续状态。”

“而且工具调用可能产生副作用，所以不能简单地从头重试。”

“如果没有执行轨迹和结构化日志，失败时也很难知道具体在哪一步出现问题。”

周衡点头。

“你看。”

“你没有说自己已经做出了完美系统。”

“但你准确解释了当前架构可能面临的工程问题。”

“这种理解也是能力证据。”

“尤其对于应届生。”

“一个可信的回答，可能是：”

> “这个项目主要让我熟悉了 Agent 的基本执行链路，也让我意识到模型能力和工程可靠性是两回事。目前我完成了其中的部分核心模块，但在长任务恢复、系统性评测和真实生产验证方面还需要补充实践。”

“它没有夸大。”

“但它清楚表达了你的理解、贡献边界和下一步方向。”

“比单纯说‘我精通 Agent 架构’更容易验证。”

## 第十幕：面试官最后记住的那句话

几天后。

陈默再次参加校招评审会议。

会议室里坐着几位技术负责人。

大家正在讨论当天的候选人。

李工翻开记录。

“林远这个候选人怎么样？”

陈默想了想。

“Java 后端基础还可以。”

“AI 应用方面，他对 Agent 的可靠执行和失败恢复有比较清晰的理解。”

“不是只会讲 ReAct 或 Function Calling 这些概念。”

“我问他工具调用失败怎么办，他能继续分析状态恢复、幂等、副作用和工作区一致性。”

“不过他的实际生产环境经验还有限，一些工程方案需要进一步验证。”

李工问：

“所以你的建议是什么？”

陈默回答：

“如果岗位要求有经验的分布式系统负责人，那他不一定合适。”

“但如果是 AI 应用工程方向的校招生，我认为可以结合基础能力和代码表现综合考虑。”

“他的优势和不足都比较明确。”

李工点头。

“行。”

会议继续。

没有掌声。

也没有任何戏剧性的逆转。

只是一个面试官能够清楚地说出：

这个候选人掌握了什么。

有什么证据。

还有哪些不足。

而这，正是林远一直在努力实现的目标。

## 第十一幕：真正的个人品牌，不是包装，而是积累

当天晚上。

林远问周衡：

“如果我要让面试官记住自己，是不是每个问题都要往 AI 工程化上靠？”

周衡摇头。

“绝对不要。”

“为什么？”

“因为那样又回到了你最初的问题。”

“面试官问 MySQL 索引，你开始讲 AI Agent。”

“面试官问 TCP 拥塞控制，你开始讲 RAG。”

“面试官问线程池，你非要扯到 Coding Agent。”

“这不是个人定位。”

“这是答非所问。”

林远笑了。

周衡继续：

“你的个人技术特点，应该通过多次真实回答自然呈现。”

“比如问 WebFlux，你能讲出模型调用场景下的非阻塞 I/O。”

“问线程池，你能讨论长时间 I/O 等待和资源限制。”

“问 MySQL，你能解释索引、事务与任务状态持久化。”

“问 Agent，你能解释工具调用和失败恢复。”

“这些回答都准确地解决了当前问题。”

“但面试官在整体上，会逐渐发现你对 AI 应用与后端工程的结合比较熟悉。”

“这才是自然形成的技术定位。”

## 第十二幕：被记住的代价

夜里十一点。

周衡准备离开。

林远突然问：

“老师，如果我一直强调自己偏 AI 应用工程化，会不会导致面试官对我的 Java 基础要求更高？”

周衡停下脚步。

“有可能。”

“什么意思？”

“任何定位都会带来相应的验证预期。”

“你说自己擅长高并发，面试官就有理由深入问线程模型、锁、缓存、数据库和性能测试。”

“你说自己擅长 RAG，面试官就有理由问检索、评测、Embedding、Rerank 和数据问题。”

“你说自己擅长 Agent，面试官就有理由问工具调用、执行状态、可靠性和安全边界。”

“所以不要轻易宣称自己精通某个领域。”

“但也不能因为害怕追问，就完全不展示优势。”

“正确做法是——”

周衡写下最后一句：

选择能够被证据支持、能够经受追问、同时与岗位相关的优势。

“你的目标不是成为一个永远不会被问倒的人。”

“而是成为一个可以被准确评价的人。”

## 终章：当面试官问起你是谁

又一个周五。

林远坐在电脑前，准备下一场 AI Agent 开发工程师面试。

这一次，他没有再修改简历里的所有技术关键词。

也没有继续增加“高性能”“高可用”“企业级”“自主研发”之类的形容词。

他打开项目代码。

找出真实提交记录。

整理自己做过的模块。

列出三个最熟悉的技术问题。

对于每一个问题，他都准备了：

- 它为什么重要；
- 自己实际做过什么；
- 为什么选择现在的设计；
- 遇到过哪些问题；
- 用什么证据验证；
- 还有哪些地方尚未解决。

做完这些，他关闭笔记。

手机上，周衡发来一条消息。

“明天如果面试官问你，你最大的技术优势是什么，你准备怎么说？”

林远想了想。

输入了一段话。

> “我的主要技术基础是 Java 后端开发，同时对 AI 应用工程比较感兴趣，也做过相关项目实践。
>
> 相比单纯调用模型 API，我更关注如何把模型能力组织成一个可执行、可验证的系统。
>
> 比如在 RAG 中，我重点关注检索结果的可靠性；在 Coding Agent 中，我关注代码分析、工具调用与修复验证；在 Java 服务端，我关注模型调用链路和流式响应的工程实现。
>
> 这些方向还有不少需要继续实践的地方，但对我实际做过的模块，我能够从代码、设计原因和问题处理过程展开说明。”

周衡过了几分钟才回复。

只有一句话。

“可以。明天不要背这段话。”

林远笑了。

他明白老师的意思。

如果这段话真的是自己对能力的总结。

那么即使不用一个字不差地背出来。

他也应该能够自然地讲清楚。

窗外，夜色渐深。

林远合上电脑。

他不再试图让所有面试官觉得自己无所不能。

他只是希望，在有限的面试时间里，对方能够看见一个真实、清楚、具有技术成长潜力的工程师。

而这一次。

他终于知道该怎么做了。

## 现实训练：如何找到真正属于你的技术优势？

周衡留下了最后一道作业。

“不要先写你最擅长什么。”

“先回忆你能够提供什么证据。”

## 技术优势证据自评

从四个方向整理自己的证据：RAG 检索与评测、Coding Agent 工程、Java 服务端工程、Java 基础与系统原理。

每个方向分别检查：能否解释原理、是否有亲自实现的案例、是否有可核实的验证材料。未做过的部分如实留空，避免用预填分数替代真实判断。

选择证据最充分的一个方向，整理至少两个具体案例、一个技术取舍和一份验证材料。章末训练提供自评清单与补充计划。
