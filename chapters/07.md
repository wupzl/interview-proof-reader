# 第7章 · 压力面试

——一个工程师真正的成熟，不是永远能够证明自己正确，而是在自己的能力受到质疑时，仍然能够冷静思考、准确表达，并接受合理的反驳。

## 第一幕：你这个项目，不就是调用几个 API 吗？

2026 年，深秋。

上午十点。

林远参加了一家大型科技公司的 AI 应用开发工程师面试。

会议室另一端坐着一名四十岁左右的技术负责人。

他叫沈岩。

据说，他负责过多个大型分布式系统，也参与过公司的 AI 基础设施建设。

面试刚开始，气氛就有些不同。

没有自我介绍。

没有寒暄。

沈岩直接打开林远的简历。

“你这个企业级 RAG 项目，是自己做的？”

“是的。”

“主要使用了哪些技术？”

“Spring Boot、MySQL、向量数据库，检索部分涉及 Embedding、BM25、重排序，模型调用通过服务端接口完成……”

林远还没说完。

沈岩就打断了他。

“所以不就是调几个 API 吗？”

林远愣住了。

“也不是，里面还是有不少技术设计的……”

沈岩继续。

“文档解析有现成库。”

“Embedding 有现成模型。”

“向量检索有现成数据库。”

“Reranker 有现成服务。”

“大模型也是调别人的 API。”

“你自己真正有技术含量的部分在哪里？”

空气突然安静下来。

林远的心跳开始加快。

他脑子里闪过无数个念头。

他是不是根本看不上我的项目？

是不是觉得我没能力？

如果我承认用了框架，是不是就等于承认项目很简单？

他下意识想反驳：

“虽然用了框架，但系统架构也是我设计的！”

可话到嘴边，他突然想起了周衡之前说过的一句话。

技术面试中，最危险的不是被质疑，而是在被质疑之后，失去分析问题的能力。

于是，他停了两秒。

没有立即反驳。

而是重新组织语言。

“您说的有一部分是对的。”

沈岩抬起头。

林远继续：

“从底层算法实现角度看，我确实没有自己训练 Embedding 模型，也没有重新实现向量数据库。”

“项目使用了成熟组件，这一点我不会包装成自己研发了底层技术。”

“但我认为，应用工程的技术价值并不只取决于是否从零实现算法，还取决于能否针对实际问题，把多个组件组织成正确、可靠、可维护的系统。”

“对于我的项目，我可以具体说明自己实现了哪些模块，做出了哪些设计决策，以及哪些部分还没有经过充分的工程验证。”

沈岩看了他一眼。

“好。”

“那你讲一个真正由你解决的技术问题。”

林远知道。

真正的面试，从现在才开始。

## 第二幕：面对质疑，第一件事不是反驳

当天晚上。

林远把这段经历告诉了周衡。

“老师，那个面试官一上来就说我的项目没有技术含量。”

“你觉得他在故意刁难我吗？”

周衡没有立即回答。

“有可能，也有可能不是。”

“什么意思？”

“我们不能只根据一句话，就判断面试官的真实意图。”

周衡打开白板。

“他的提问可能包含三种不同的情况。”

第一种：正常验证技术深度

面试官想区分“调用现成组件”和“真正理解系统设计”的差别。

第二种：对项目价值存在不同判断

他可能认为某些功能确实比较常规，希望了解你做过的非标准化工作。

第三种：不恰当的压力或贬低

面试官可能使用不尊重的表达，甚至持续进行没有技术依据的否定。

周衡说：

“这三种情况，表面上可能非常相似。”

“但你不能把所有质疑都理解为攻击。”

“也不能把所有攻击都合理化为正常考察。”

“最有用的做法是先找出提问中可以验证的技术命题。”

林远问：

“比如他说我只是调用 API？”

“对。”

“这个问题可以转换成——”

> 在大量使用成熟组件的前提下，你本人解决了哪些并非简单调用 API 就能自动完成的工程问题？

“这样一转换，你就知道应该回答什么。”

“而不是陷入‘我的项目到底有没有技术含量’这种抽象争论。”

## 第三幕：一次失败的反击

周衡突然说：

“我们来模拟。”

他坐到林远对面。

语气变得冷淡。

“你这个 RAG 项目很普通，网上教程一大堆。”

林远回答：

“但我做得比较完整，里面用到了很多技术。”

“哪些技术？”

“Spring Boot、Redis、MySQL、Embedding、Reranker、混合检索……”

“这些别人也会。”

“但是我自己实现了这些功能。”

“实现了又怎么样？照着教程也能做。”

林远开始着急。

“我不是照着教程做的！”

周衡继续。

“那你怎么证明？”

林远一时语塞。

周衡停止了模拟。

“你发现问题了吗？”

“我一直在解释我不是抄的。”

“对。”

“你陷入了一个无法有效验证的争论。”

“因为你反复强调‘我自己做的’，并没有提供新的证据。”

“面试官可以继续说‘我不相信’。”

“你就继续反驳。”

“最后整场面试变成情绪对抗。”

周衡在白板上写下：

> 有效回应 = 识别命题 + 承认边界 + 提供证据

“你不要和面试官争夺谁有资格定义技术含量。”

“你要把问题拉回可验证的事实。”

## 第四幕：怎样用三句话化解质疑？

周衡重新扮演面试官。

“你的项目不就是调 API 吗？”

林远这次回答：

“底层模型和向量检索确实使用了现成组件，我没有重新实现它们。”

“但我自己负责的工作包括具体的业务链路实现，以及相关的工程设计。”

“如果您希望判断技术深度，我可以选一个实际处理过的问题，从问题出现、原因定位、方案选择到最终实现展开讲。”

周衡点头。

“这次好在哪里？”

林远回答：

“没有否认客观事实。”

“没有和面试官争论。”

“而且把话题转移到了实际解决的问题上。”

“对。”

“但还有一个关键。”

“什么？”

“你后面必须拿得出真实案例。”

“假设你说自己解决了 SSE 流式输出的工程问题，那面试官就有理由问：”

“连接中断怎么办？”

“客户端取消后，上游请求有没有取消？”

“模型接口返回一半失败了怎么办？”

“消息是先保存还是后保存？”

“如果数据库持久化失败，但客户端已经收到部分 Token，该如何处理？”

“如果这些问题你一个都没考虑过，那么前面三句话再漂亮也没有意义。”

林远慢慢点头。

压力面试最有效的防御，不是更强硬的语言，而是足够扎实的事实。

## 第五幕：真正的技术深度，藏在那些不起眼的 Bug 里

周衡打开林远曾经开发的 Java AI 聊天项目。

“我们不说虚构的优化成绩。”

“就拿你实际处理过的一个问题。”

“比如你的聊天消息采用树形结构。”

林远点头。

“用户编辑历史消息，可以创建新的对话分支。”

“重新生成 assistant 回复，也需要挂接在正确的父消息下。”

“没错。”

周衡继续。

“假设面试官问，这个不就是数据库存消息吗？”

“你准备怎么回答？”

林远思考片刻。

“我会先解释，普通的线性聊天记录和支持编辑、重新生成的消息树不完全相同。”

“线性结构只要按照时间排序就能展示。”

“但消息树需要区分不同分支，并在用户切换版本时恢复对应的祖先消息链。”

周衡点头。

“继续。”

“比如用户消息 U1 对应 assistant 回复 A1。”

“用户选择重新生成时，新生成的 A2 应该仍然以 U1 作为父节点。”

“而不是错误地把 A1 当成父节点，否则结构会从兄弟分支变成串行对话。”

“如果用户编辑了 U1，那么修改后的消息应该形成另一条分支，后续回复也需要挂在新的用户消息上。”

周衡笑了。

“你看，这就是一个非常好的实际例子。”

“它不是多么高深的算法。”

“但是它展示了你对数据模型和业务语义的理解。”

“更重要的是，你可以解释为什么原来的实现不对，后来如何修改，以及如何测试分支切换是否正确。”

林远忽然明白。

他以前总觉得，只有讲分布式锁、百万 QPS、复杂算法，才能体现技术深度。

但有时候，一个真实处理过的消息树 Bug，反而比虚构的高并发架构更有说服力。

因为它能够提供完整的工程证据链。

消息树的一个简化示意

示意：重新生成回复形成同一用户消息下的兄弟节点；编辑历史用户消息形成新的对话分支。

周衡说：

“这就是你要建立的习惯。”

“每个项目至少准备几个真实问题。”

“不是背一个完美故事。”

“而是能够从真实代码、错误、原因和修复过程出发，解释自己的工作。”

## 第六幕：当面试官说“你根本不懂底层”

第二天。

压力训练继续。

这次，周衡扮演一位对基础知识要求很高的面试官。

“你说自己熟悉 Spring WebFlux。”

“那你不用 WebFlux，能不能自己实现一个 SSE 服务？”

林远回答：

“可以考虑使用 Servlet 提供的异步能力，也可以使用更底层的网络框架实现。”

周衡继续。

“我问的是你能不能从底层实现。”

林远思考了几秒。

“如果是基于 HTTP 的 SSE 协议，实现基础版本并不复杂。”

“服务端需要返回 `Content-Type: text/event-stream`，保持连接并持续写入符合 SSE 格式的数据。”

“例如使用 `data:` 字段和空行作为事件分隔。”

“但如果要实现具有生产可靠性的服务，还需要考虑连接生命周期、数据缓冲、慢客户端、代理超时、断线重连和资源释放等问题。”

周衡点头。

“那如果客户端断开连接，你怎么知道？”

“具体取决于服务器和网络框架。”

“可能在后续写入时发现 I/O 错误，也可以依靠框架提供的取消或连接关闭信号。”

“但不能假设客户端一关闭浏览器，服务端就一定立即同步收到通知。”

“很好。”

“如果上游模型还在持续生成 Token 呢？”

“需要考虑下游取消信号能否向上游传播。”

“如果无法取消上游请求，即使客户端已经断开，后台仍然可能继续消耗模型资源和 Token 成本。”

周衡停止了提问。

“你看，这一轮考察的真正能力是什么？”

“从框架的使用，推导到底层协议和资源管理。”

“对。”

“你不一定需要自己写过一个完整的 HTTP 服务器。”

“但如果你声称理解 WebFlux，你至少应该能够解释它依赖的基本机制，以及框架替你完成了哪些工作。”

“不过也有边界。”

“什么？”

“如果面试官要求你现场写一个高性能 Netty 实现，而岗位并不要求这些能力，你答不上来也不能直接证明你不会 WebFlux。”

“不同抽象层次对应不同能力。”

“熟练使用框架、理解框架原理、能够重新实现框架，是三个不同的要求。”

“面试中不要把它们混成一回事。”

## 第七幕：一次真正危险的反问

下午。

沈岩再次出现在模拟面试里。

“你的项目没有线上流量，所以我不认为它算企业级。”

林远回答：

“如果企业级指已经经过生产规模验证，那我的项目确实没有充分证据支持这个表述。”

“但是我在设计时考虑过一些企业应用需要的能力，比如权限控制、异常处理和服务模块化。”

沈岩继续。

“考虑过有什么用？谁都能考虑。”

林远停了一下。

这句话已经带上了明显的否定意味。

但他没有立即反击。

“您说得对，设计方案和实际验证之间确实存在差距。”

“如果您希望评估我的工程能力，我可以先介绍已经实际完成的部分，比如权限认证、消息持久化和流式模型调用。”

“至于高并发或生产稳定性，我不会把没有经过验证的设计说成实际成果。”

沈岩问：

“所以你承认自己工程能力不足？”

林远看着镜头。

“我承认自己在真实生产环境中的经验有限。”

“但这与完全不具备工程能力不是同一个结论。”

“我已经完成过实际功能开发，也处理过相关的实现问题。”

“我的不足主要集中在生产环境的性能验证、可观测性和故障处理经验，这些方面仍需要进一步积累。”

沈岩沉默了几秒。

“好，继续。”

模拟结束。

周衡笑了。

“你刚才做得很好。”

“因为你没有接受一个过度扩大的结论。”

林远问：

“什么意思？”

“面试官说‘没有线上验证’，这个事实可能成立。”

“但从这个事实直接推出‘没有任何工程能力’，逻辑上并不充分。”

“你应该承认真实的不足，但不需要接受没有证据支撑的全面否定。”

周衡在白板上写下：

承认具体不足，不等于接受笼统否定。

## 第八幕：什么时候应该反驳面试官？

晚上。

林远提出了一个一直困扰他的问题。

“如果面试官说错了，我到底应该反驳吗？”

周衡回答：

“当然可以。”

“但不要把反驳当成争胜负。”

“技术讨论中最重要的是把事实说清楚。”

他拿出一道 JVM 问题。

“假设面试官说——”

“G1 的垃圾回收过程全部可以并发执行，不需要 STW。”

林远立即回答：

“这个说法不准确。”

周衡问：

“然后呢？”

“G1 的并发标记阶段确实可以与应用线程并发执行，但常规 Young GC 和 Mixed GC 的 Evacuation 阶段需要 STW。”

“因此不能认为 G1 整个垃圾收集过程都是并发的。”

“很好。”

周衡继续：

“那你在面试里应该怎么说？”

林远调整了一下措辞。

> “我理解这里可能需要区分 G1 的并发标记与对象疏散阶段。G1 的并发标记可以与应用线程同时执行，但 Young GC 和 Mixed GC 中的对象转移通常需要暂停应用线程。如果我们讨论的是 G1 的常规回收过程，我认为不能说它完全没有 STW。”

周衡点头。

“注意，你没有说‘老师你错了’。”

“也没有为了迎合面试官，放弃自己知道的事实。”

“你直接解释了技术依据。”

“如果对方继续坚持，你可以结合 JDK 官方文档或具体版本讨论。”

“如果一时无法确认，就明确说需要核实，不要凭印象争论到底。”

林远点头。

“所以反驳不是态度问题，而是证据问题。”

“对。”

## 第九幕：有些面试官，不值得你证明自己

夜里。

周衡突然说：

“我们还要讨论另一种情况。”

“什么？”

“如果面试官持续进行人身攻击怎么办？”

林远愣了一下。

“比如？”

周衡说：

“假设对方不再讨论项目、代码或技术事实。”

“而是不断说——”

“你这种学校的学生能懂什么？”

“你是不是根本没有脑子？”

“你做这些东西纯粹浪费时间。”

“这类表达与正常技术质疑不同。”

“你应该怎么办？”

林远沉默。

“继续解释？”

周衡摇头。

“没必要无限解释。”

“你可以保持职业化，尝试把对话拉回具体问题。”

例如：

> “如果您对我的项目实现有疑问，我愿意解释具体代码和技术方案。不过我希望我们主要围绕岗位要求和技术能力展开讨论。”

“如果对方仍然持续侮辱，你可以选择结束面试。”

林远问：

“可是这样不是直接失去机会了吗？”

周衡看着他。

“有可能。”

“但你需要知道，面试不是任何行为都必须忍受的场合。”

“你可以接受严格的技术考察。”

“可以接受项目被质疑。”

“可以接受自己的答案被指出错误。”

“但没有义务接受持续的人身羞辱。”

“而且，面试官的行为本身也提供了团队文化方面的信息。”

## 第十幕：压力面试真正考察的能力

几天后。

林远再次坐在沈岩对面。

沈岩打开简历。

“你说自己做过多模型适配器。”

“我觉得这个设计很简单。”

“不同模型不就是换一个 URL、换几个参数吗？”

林远思考了一下。

“如果只适配少量兼容 OpenAI 接口的模型，确实可能只需要做少量参数转换。”

“但如果模型的消息格式、推理输出、工具调用和流式事件结构不同，那么适配层需要解决的不仅是请求地址问题。”

沈岩问：

“具体举例。”

“比如普通聊天模型可能只输出 `delta.content`，但有些推理模型会额外返回 `reasoning_content`。”

“如果上层业务直接依赖供应商原始响应，就容易把模型特有字段传播到整个系统。”

“因此可以设计统一的内部流式事件模型，在适配层解析供应商响应，再转换成上层能够稳定处理的事件。”

沈岩继续：

“那如果一个模型的工具调用参数是分片返回的呢？”

林远回答：

“那不能假设每个 SSE 事件都包含一个完整的工具调用参数对象。”

“需要根据调用标识和事件语义进行增量组装，直到达到该协议定义的完成条件。”

“同时还要处理取消、异常结束和不完整参数的问题。”

沈岩又问：

“如果不同模型的工具调用语义根本不一样呢？”

林远思考片刻。

“那统一适配层不能为了形式上的统一，抹掉重要的语义差异。”

“可以抽象共有能力，同时保留模型能力声明和供应商特有扩展。”

“上层业务根据模型能力决定是否启用某些功能。”

“否则只是把不兼容的问题隐藏起来，最终可能在运行时出错。”

沈岩点头。

“这个回答有点内容。”

林远没有露出明显的兴奋。

因为他已经不再把对方每一句评价当作自己价值的最终裁决。

他只是认真回答问题。

## 第十一幕：压力下，如何组织自己的答案？

面试结束后。

周衡给林远留下最后一个方法。

“以后遇到很尖锐的技术质疑，你可以采用四步。”

1. 第一步：识别具体质疑

   对方是在质疑项目真实性、技术深度、指标依据，还是实际工程经验？
2. 第二步：承认成立的部分

   不要为了维护自尊，否认客观事实或自己的实际局限。
3. 第三步：提供一条完整证据链

   选择最熟悉的真实问题，说明现象、原因、方案、实现和验证结果。
4. 第四步：保持可讨论性

   允许面试官进一步追问，也允许自己的结论在新证据下被修正。

“例如对方说，你的 RAG 只是调 API。”

“你可以承认底层组件确实使用了现成方案。”

“然后说明自己在哪条工程链路上做了实际工作。”

“如果对方说你不懂高并发。”

“你不要急着背 Redis 缓存雪崩。”

“先看他质疑的具体依据。”

“是没有压测数据？”

“还是线程池设计错误？”

“还是数据库连接池容量不合理？”

“针对不同的问题，拿出对应证据。”

“你需要的是准确回应，不是情绪反击。”

## 第十二幕：一场没有赢家的争论

最后一次模拟。

沈岩问：

“你知道吗？我觉得你现在这些 AI 项目，技术门槛都不高。”

林远没有立即回答。

他思考片刻。

“如果与底层模型训练、编译器、数据库内核等方向比较，一些 AI 应用项目的底层算法门槛确实可能相对较低。”

“但应用工程的复杂度取决于具体任务。”

“简单的问答 Demo 和需要可靠执行、权限隔离、可观测性、评测与故障恢复的 Agent 系统，工程难度并不相同。”

沈岩说：

“可那些工程问题，也都已经有成熟方案了。”

林远回答：

“成熟方案确实能够减少重复开发。”

“但选型、集成和验证仍然需要结合业务约束。”

“比如一个 Agent 的任务恢复，如果涉及数据库状态、工具调用副作用和外部服务幂等性，不能简单地说接入某个框架就自动解决。”

沈岩继续：

“所以你认为自己的项目很厉害？”

林远摇头。

“我不想通过一个笼统的形容词评价项目。”

“它确实还有不少不足，尤其在生产环境验证和系统化评测方面。”

“但我认为可以通过具体实现和问题解决过程，评价它体现了哪些工程能力。”

沈岩看着他。

几秒钟后，突然笑了。

“你倒是挺能坚持自己的判断。”

林远回答：

“如果有新的技术依据，我也愿意修正判断。”

会议室安静下来。

这一次。

双方没有谁赢。

也没有谁输。

但林远终于学会了一件事。

他不需要在面试中赢过面试官。

他需要做的，是让技术讨论始终围绕事实、逻辑与证据展开。

## 终章：真正的底气来自哪里？

深夜十一点。

林远回到宿舍。

他打开电脑。

看见自己这些日子整理的面试笔记。

里面有各种各样的知识。

JVM。

MySQL。

Redis。

计算机网络。

操作系统。

RAG。

Agent。

系统设计。

他突然意识到，以前自己最害怕的，并不是不会某个技术问题。

而是面试官一句否定，就让他开始怀疑自己做过的一切。

“你这个项目没技术含量。”

“你这些数据是不是编的？”

“你对工程化理解不够。”

“你是不是只会调 API？”

过去，这些话会让他迫切地想证明自己。

证明自己的项目很复杂。

证明自己技术很好。

证明自己值得被录用。

而现在。

他开始能够区分：

哪些质疑有事实依据。

哪些只是观点分歧。

哪些问题真正暴露了自己的知识短板。

哪些评价超出了现有证据。

他在笔记本最后写下：

> 如果面试官指出了我的错误，我应该感谢这个错误被发现，并认真修正。
>
> 如果面试官质疑我的项目，我应该拿出真实的实现和证据。
>
> 如果面试官的判断缺少依据，我可以平静地提出不同意见。
>
> 如果我确实没有做过某件事，就不应该为了通过面试而声称自己做过。
>
> 真正的技术自信，不是确信自己永远正确，而是知道如何判断自己是否正确。

他合上电脑。

这次，他没有继续猜测面试官究竟对他满意还是不满意。

因为那些事情，已经不完全由他控制。

他能控制的，是下一次面对技术问题时，是否能够拿出更准确、更完整、更可信的答案。

## 现实训练：四种质疑，四种回答策略

假设你正在参加 AI 应用开发工程师技术一面，面试官突然说出下面四句话。

本章训练将围绕四类质疑展开：项目是否只是调用 API、框架之外的理解、性能数据的依据，以及个人贡献的边界。先承认合理的限制，再给出具体证据，最后说明验证办法。
